# 亮度上限守护 · 0.2.0 实验版

目标是小米 17 Pro Max / 澎湃 OS 3 上的**温度造成的最高亮度上限**：例如手动拉满原本约 500 nit，发热后仍只能约 300 nit。模块检测显示服务的热亮度上限，并在识别到支持的接口时尝试绕过该限制。它不会通过循环拉满亮度实现效果。

用户反馈 0.2.0 在小米 17 Pro Max、澎湃 OS3.0.319.0.WPBCNXM / Android16 / legacy-82 上实测可用。该反馈未提供分功能测试范围、光学亮度测量或长期稳定性结果；不代表所有固件兼容。构建通过 48 项策略/反射、24 项显示回调模拟和 38 项监测检查，共 110 项主机检查。

## 安装和启用

1. 使用传统 LSPosed API 时安装 `PopsicleBrightnessGuard-0.2.0-legacy.apk`。与 0.1.0 使用相同包名、签名，保留原开关和温度阈值。只有你的 LSPosed 明确支持 **libxposed API 101** 时，才选 `modern.apk`。两包选一个；API 100 框架不能加载 101 版。
2. 在 LSPosed 启用“亮度上限守护”，作用域选**系统框架 / System Framework**。现代版元数据里的系统服务作用域是 `system`，由兼容的管理器显示。不要只选系统界面 System UI。
3. 重启一次，打开桌面的“亮度上限守护”。开机完成后约 12 秒开始采样，保持界面打开，再等 2–4 秒看连接状态。
4. 默认仅诊断。先确认“主屏身份：已核验”和“已匹配拦截接口”大于 0，再点击“启用热限亮拦截”。在 SukiSU 授予这个应用 Root 权限，用来保存模块自己的开关和温度阈值。
5. 保持原来手动亮度设置，在平常能触发问题的使用场景中观察。模块已启用后不需要界面一直运行；显示服务内的钩子与采样继续工作。

“已匹配拦截接口 > 0”只代表方法签名已匹配，不保证手机当前的热限亮一定走此入口。主屏核验还会在每次实际拦截前检查。

## 新增：实时亮度与上限监测

监测与拦截开关独立：即使系统严重过热导致拦截暂停，监测仍工作。主屏框架每秒采样，保留最近 90 秒曲线和可导出的 JSON。

- **框架当前输出**：显示服务准备发送的逻辑亮度，可看到与上秒相比上升/下降多少；不是光学实测。
- **当前最高上限**：读取系统 BrightnessInfo 的上限及原因。当前输出不变而上限降低，也会显示上限下降。
- **亮度请求**：手动模式使用框架的屏幕亮度设置；自动模式优先读取新鲜的限亮前请求，读不到就显示未知，不把自动模式下保存的整数设置强行当成请求。
- **系统映射估算 nit**：有有效映射时换算 SDR 输出和当前最高上限，标注“非实测”。映射缺失时显示未知，绝不直接把 0–1 乘以一个假定 nit 上限。
- **小米热上限**：实时读报告已发现的厂商显示字段，保留原始单位，记录其上限值是否降低。字段变化只证明该字段数值变化，不保证限制已应用到面板。

颜色：蓝色为框架输出、绿色为请求、橙色为系统最高上限。保持亮度稳定约 3 秒建立对照；需要重新取样时点“清除曲线，重新建立亮度对照”，保存后会清空对照和曲线，保留拦截开关。

| 状态 | 能确定什么 |
| --- | --- |
| 系统明确报告最高亮度受热限制 | 系统给出的上限原因是温控，且上限有效 |
| 最近热调整调用降低了亮度请求 | 已识别热调整方法确实返回更低值，观察窗口约 3.5 秒 |
| 最近热调整已被绕过 | 软件回调被处理，面板效果仍需验证 |
| 检测到内部热上限 / 小米热上限数值下降 | 观察到内部字段；不能单凭缓存字段认定已实际降亮 |
| 请求未变，主屏框架输出下降 | 手动请求未改变、对照有效、输出显著下降；原因未必是温控 |
| 主屏框架输出下降，原因待确认 | 如自动亮度模式下输出降低，不能直接归因温控 |
| 最近最高上限下降，原因待确认 | 确认最高上限数值降低，但没有充分热限制证据 |

每秒变化会显示细小数值下降；额外的“输出下降记录”要求降低至少 0.01 且至少为对照值的 12%，用来排除噪声。熄屏、唤醒、采样间隔过长、显示身份/手动请求改变、应用窗口覆盖、正在进行的亮度动画会重建对照或单独提示。动画期间仍显示每秒数值变化，不直接判为异常。

## 新增：Root 驱动背光读取

点击“开启 Root 背光读取”，按需在 SukiSU 授权。一个持续的 `su` 会话每秒只读 `/sys/class/backlight/*` 下的 `brightness`、`actual_brightness`、`max_brightness`、`bl_power`，以及存在时的 `/sys/class/thermal/thermal_message/max_brightness`。

`actual_brightness` 是驱动回报值，刻度比例不是物理亮度百分比。节点名不自动证明它属于主屏；本版把主屏/背屏未知的节点明确标注为身份未核验，节点变化不冒充主屏热限亮。手机没有可读节点时仍可使用框架监测。

背光读取仅在界面可见时运行，离开界面会关闭该 Root 会话。返回界面会重新连接；框架监测和已启用的显示钩子继续运行。导出的报告同时附带最近的背光读数及其采样时间。

## 这一版会做什么

- 小米 `DisplayPowerControllerImpl.adjustBrightnessByThermal(float, …)`：先运行原方法。如果明确返回比调用者请求更低的值，条件允许时返回原请求。它不额外申请 HBM 或超出原请求的亮度。
- Android 16 `BrightnessThermalModifier`：只跳过已识别签名的热限亮 `apply` / `applyStateChange`。电量、功率、HDR、其他显示限制仍由原来的其他组件处理。
- 存在旧版 `BrightnessThrottler` 时：对主屏热上限 getter 返回正常上限，保留内部真实热状态和温度监听。
- 记录接口、字段、主屏识别、热限制值、处理次数、框架输出变化，以及已识别的厂商显示温控信号。日志为有限长度的内存记录，重启会清空；打开界面可导出 JSON。

自动亮度曲线、CPU/GPU 频率、全局温控服务、温度传感器读数、`/vendor` 温控配置以及 sysfs 节点均不由模块改写。模块只请求重新计算显示亮度，保留系统原监听。

## 温度和适配条件

设备门槛：`Build.DEVICE=popsicle`，`Build.VERSION.INCREMENTAL` 以 `OS3.` 开头，Android SDK 35/36。这里是运行时门槛，不是对所有澎湃 3 版本的真机适配承诺。身份不匹配时仅诊断。

默认电池温度达到 **45℃** 时暂停绕过，回落至 **43℃** 才恢复；可在 38–48℃ 之间调整，调整后点击启用保存。这个阈值是模块的退出条件，**不是保证面板安全的温度，也不是手机原有的限亮阈值**。

系统报告严重过热及以上（热状态 ≥ 3）、热状态未知、电池读数缺失、读数超过 12 秒、屏幕未唤醒、主屏身份未确认或累计三次模块异常时，放行原亮度限制。这样仍可能在严重发热时降上限。已有模块若伪造温度/热状态，会影响这些判断；此版没有验证与其联用的效果。

## 判断结果与继续适配

| 现象 | 含义 / 下一步 |
| --- | --- |
| 未连接系统框架 | 检查 LSPosed 启用状态、作用域、API 版本和是否重启；保持界面打开等一次采样 |
| 未匹配到可拦截接口 | 当前系统显示实现不在第一版适配范围，导出诊断报告 |
| 接口已匹配，主屏未核验 | 亮度对象身份尚未识别；导出报告，不把它当作成功 |
| 热限亮调用增加，拦截调用为 0 | 查看暂停原因；也可能该调用属于背屏/身份不明的屏幕 |
| 拦截调用增加，肉眼仍变暗 | 可能有额外厂商路径、驱动/面板限制或模块冲突；导出报告和冷/热对照诊断 |
| 框架输出下降 | 仅说明框架输出降低；不能凭这个数认定热限亮，也不能换算成 nit |

应用 →“导出诊断报告”，分别保留问题发生前和发生后的报告。报告含机型代号、系统版本、温度、接口清单、显示对象身份、计数与最近事件；不自动上传。若仍不命中，可结合随附的只读 `brightness-diagnose.sh` 采集冷/热的 `dumpsys display`、热状态和背光节点，才能判断需追加哪个入口。脚本读取系统状态，只把报告写到 Download；也未经该机真机验证。

**LSP 无法保证解除 Java 层以下的驱动、面板固件或原生厂商服务限亮。** 本版没有硬编码 500/300 nit：系统数值可能是 0–1、逻辑背光值等，真正 nit 需要屏幕映射和测量证据。

## 关闭与恢复

先在应用点击“关闭拦截，保留诊断”，授权保存后约 1 秒停止绕过，并请求显示服务重算。Root 背光读取可用自身按钮单独停止。如果连接已异常、仍有问题或希望完全停用，在 LSPosed 关闭模块并重启。关闭钩子后恢复系统原逻辑。

应用无法打开时，可在具有 Root 的终端执行：

```sh
su -c 'settings put global popsicle_brightness_guard_enabled 0'
```

随后在 LSPosed 关闭模块并重启。三个配置键只属于此模块；卸载不自动删除它们，重新安装会沿用已保存的开关。需要清空时分别执行：

```sh
su -c 'settings delete global popsicle_brightness_guard_enabled'
su -c 'settings delete global popsicle_brightness_guard_limit'
su -c 'settings delete global popsicle_brightness_guard_reset'
```

如果出现系统进程异常或重启循环，按你使用的 LSPosed/Root 管理器的模块救援方式停用本模块，再启动。系统框架钩子属于实验性修改；开始验证前要知道本机的模块停用方法。

## 从源码构建

这是 Windows 上使用 Android 官方工具直接构建的源码包，不含 Gradle 包装器。需要 Python 3.9+、JDK 21、Android SDK Platform 36 和 Build Tools 36.1.0；两个官方编译期 API JAR 随源码附上，不打入 APK。

```powershell
python build.py --sdk 'C:\路径\Android\Sdk' --jdk 'C:\路径\jdk' --out '.\dist'
```

构建会先运行检查，再生成两个 APK、签名并验证。首次构建在 `build/experimental-signing.p12` 生成本地实验签名；该私钥不随源码发布；仓库和 Release 不包含签名私钥。自行构建的包签名与发布 APK 不同，通常需卸载发布包再安装。保留自己的密钥，便于以后覆盖更新。

`tests/fixtures` 是主机检查的假 Android/显示类，**不进入 APK**。`build-verification-0.2.0.json` 保存实际构建结果与 SHA-256。源代码许可与引用出处见 `LICENSE`、`THIRD_PARTY_NOTICES.md`、`分析与实现.md`。
